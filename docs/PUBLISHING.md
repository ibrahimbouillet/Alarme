# Publishing ALARM

ALARM is developed by **Ibrahim Bouillet** and distributed under the MIT License.
No account, service key or external server is required to run the alarm.

## Prepare a release

From the source checkout, with the UCRT64 build tools on PATH:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\package.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\export-source.ps1
```

The first command builds and tests ALARM, then creates the Windows x64 portable
ZIP and a SHA-256 file in `out/releases`. The second creates a source ZIP from
the current working tree, including uncommitted public changes. It excludes Git
history, private archives, local settings, generated packages and build output.
Neither command commits, stages or publishes anything.

Keep the LICENSE and bundled runtime notices in the distribution. The release
application, graphical installer and PowerShell scripts are unsigned.

## Build the Windows installer

The installer is a self-contained, per-user Windows 10/11 x64 executable built
with [Inno Setup 6.7 or newer](https://jrsoftware.org/isdl.php). Install the compiler on the
packaging machine; users do not need it. Its green artwork is generated by the
packaging script from the checked-in branding source.

Create the portable ZIP first with `scripts/package.ps1`, then extract that exact
payload and wrap it with the installer. From the repository root:

```powershell
$releaseZip = (Resolve-Path 'out\releases\ALARM-0.6.1-windows-x64.zip').Path
$payload = Join-Path (Get-Location) ('.local\installer-payload-' + [guid]::NewGuid().ToString('N'))
Expand-Archive -LiteralPath $releaseZip -DestinationPath $payload
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\package-installer.ps1 -PayloadDirectory $payload -OutputDirectory out\releases -IsccPath 'C:\Program Files (x86)\Inno Setup 6\ISCC.exe'
```

Use `-IsccPath` to select a different compiler installation. The output is
`out/releases/ALARM-0.6.1-windows-x64-setup.exe` and its `.sha256` file. The setup
wizard installs into `%LOCALAPPDATA%\Programs\ALARM`, creates the Start menu
shortcut and registers an uninstaller. It does not enable an alarm or launch
ALARM automatically. Uninstallation preserves personal settings and logs.

When adding an installer to an existing release, use the ZIP already published
on that release as `$releaseZip`, verify it against its published SHA-256, and
run the extraction and installer command above. Do not silently rebuild or
replace the released application binary. The graphical installer can be added
without moving the existing `v0.6.1` tag or replacing the portable ZIP.
The graphical package supplies the current `INSTALL.md` as its installed
`README.md`, so its instructions describe the graphical installer rather than
the legacy scripts that are only included in the portable ZIP.

Run the real installer lifecycle smoke test with a clean Windows user:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\test-installer.ps1 -InstallerPath out\releases\ALARM-0.6.1-windows-x64-setup.exe -PayloadDirectory $payload
```

The test refuses to run if an ALARM installation, shortcut or process already
exists. It uses a unique validation directory, checks refusal of an occupied
folder, installs silently, compares the installed executable's SHA-256 with the
payload, checks registration and shortcuts, reinstalls with settings and unrelated
file fixtures, then uninstalls. It verifies that owned files are removed and
fixtures and existing personal data remain intact. It never recursively removes
the test directory. Its report and private setup logs remain under
`.local/installer-validation`; do not publish logs containing local paths.

On an interactive machine with audio, add `-RunIntegration` to run the installed
application's accelerated integration test with an isolated `--data-dir`. CI omits
that option because hosted runners cannot establish physical audio behavior.
Also inspect the visible wizard and application launch. Test sound and wake separately on the intended
hardware using [the manual checks](MANUAL_VALIDATION.md); successful packaging
does not establish those behaviors.

## Upload release assets

After reviewing and validating the output, add the installer and checksum to
the existing release with authenticated GitHub CLI access:

```powershell
gh release upload v0.6.1 out/releases/ALARM-0.6.1-windows-x64-setup.exe out/releases/ALARM-0.6.1-windows-x64-setup.exe.sha256 --repo ibrahimbouillet/Alarme
```

Keep the portable ZIP and its checksum as alternate downloads. In the release
notes, put the [Windows installer](https://github.com/ibrahimbouillet/Alarme/releases/download/v0.6.1/ALARM-0.6.1-windows-x64-setup.exe)
first and identify GitHub's generated **Source code** archives as source-only.
Mention that the application and installer are unsigned and may trigger a Windows
SmartScreen unknown-publisher warning. Download the uploaded installer again,
verify its SHA-256 against the local output, and check the visible asset list.
Uploading a package alone is not evidence of a clean-machine installation test.

## Personal reports and existing history

Machine-specific development reports are preserved locally under
`.local/publication-archive/`, which is ignored by Git. Do not upload `.local/`,
build output, user configuration or raw diagnostics as repository source.

Removing a file from the working tree does **not** remove it from earlier commits.
The public repository starts with an independent clean history. Earlier private
development history is retained separately and is not an ancestor of the public
release. Do not merge or push branches or tags from a private development archive
into the public repository.

For a similar migration, extract the clean source ZIP into a new directory and
create a fresh repository there. Keep the original repository private and update
its local remote before reusing its old GitHub name for the new repository.

GitHub's generated source ZIP follows the committed repository contents. The
local source export is intended for preparing that clean first commit; it is not
a replacement for reviewing the final files you choose to commit.

## Automated checks

The Windows workflow builds with GCC UCRT64 and runs the deterministic engine,
timing and widget-state tests. It uses the runner's preinstalled Inno Setup 6 to
wrap the same ZIP payload, runs the real silent installation/reinstallation/removal
smoke test, then uploads the portable ZIP, graphical EXE installer and SHA-256
files as workflow artifacts. Private validation logs are not uploaded. It does not
publish a GitHub release.
It does not establish physical wake, speaker audibility or
lock-screen presentation. Run the full local suite and the relevant manual checks
before describing those behaviors as tested on a particular device.

The optional liquid demo and widget provider are developer experiments and are
excluded from the ordinary alarm release.
